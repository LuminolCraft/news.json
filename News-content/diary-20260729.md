# 开发日记：Sidebar 动画调试记

**日期**：2026-07-29

---

## 问题

Minecraft 计分板插件，写了动画功能但客户端始终停在第第一帧不切换。

## 排查之路

一开始怀疑是第三方库的渲染链路有问题，花了大量时间通读 scoreboard-library 源码——`ComponentSidebarLayout.apply()` → `SidebarComponent.draw()` → `LineDrawable.drawLine()` → `AbstractSidebar.line()` → tick 队列 → 发包。整个管线逻辑正确，数据包确实发出去了，客户端该收到。

然后怀疑多线程可见性。Folia 把任务调度拆成了全局区域线程和异步线程池，普通 HashMap 在跨线程时可能读到过期数据。换成 ConcurrentHashMap，没用。

最后才意识到应该**让代码自己说话**。在关键节点加了几行日志：

```
[DEBUG] getSidebar key=default isSimple=true hasAnimation=true
[DEBUG] Updating task... (每秒20次，证明调度在跑)
```

两行日志拼在一起，答案就出来了：**动画数据注册的逻辑跑了，但注册结果没有传到调度任务手里。**

回看代码，发现动画实例的创建和 `map[anim] = interval` 写在 Supplier lambda **里面**，而这个 lambda 只在 `layout.apply()` 时才执行。遍历 `animationIntervalMap` 注册到全局 map 的代码却跑在 `apply()` **之前**——典型的时序错位。执行时 map 空的，什么都注册不进去。

## 解法

把动画实例的创建和注册逻辑从 lambda 内提到函数体外，让它在 `buildSidebar()` 阶段就跑完；Component 拼接和 `currentFrame()` 留在 lambda 内，保证每次刷新重新取帧。

## 启示

**加日志比读源码快。** 读了两小时源码，不如三行 `println` 定位得准。遇到"明明逻辑对但结果不对"的情况，先用日志画一张**时序图**——看代码到底是按什么顺序执行的，往往比静态分析省十倍时间。

**不要跳过最简假设。** 从"库的渲染管线有问题"到"多线程可见性"都是合理的怀疑，但实际原因简单到令人尴尬——填充 map 的代码根本没跑到。调试时优先验证最直接的假设：这段代码真的被执行了吗？
